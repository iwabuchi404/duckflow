# Vitals 再設計: 自己申告（UX）と実測テレメトリ（制御）の分離

**ステータス:** 設計合意済み・未実装
**作成日:** 2026-06-13
**関連:** `docs/edit_format_search_replace_design.md`（テレメトリ活用の思想系列で接続）

---

## 1. 背景: 2つの立場とその統合

### 1.1 課題（システム側の視点）

- LLMの自己申告スコアは較正されていない。特に弱いモデルは正誤に関わらず高値（0.85〜0.95）に張り付くことが知られている（Xiong et al. 2023, Kadavath et al. 2022）。
- 較正されていない値で実行を制御する（safety < 0.5 でゲート）のは、安全の実体がない。
- 「全アクションの前に4次元」の申告要求はトークン税・遵守負担であり、プロンプト効率の設計目標と矛盾する。現に表記ゆれ修復の正規表現が4本ある＝モデルがフォーマットすら守れていない。

### 1.2 価値（コンセプト側の視点 — 本設計で守るもの）

- **自己申告は「ユーザーへの伝達チャネル」であり、Companionコンセプトの核。** 弱いモデルは出力の流暢さと正しさが乖離するため、ユーザーは文面から信頼度を判別できない。「自信がない」という表明は、ユーザーがその出力をどう読むべきかの判断材料になる。
- 自己申告には代替不可能な情報がある: 実測テレメトリは**過去**（直近の成功率）しか測れないが、自己申告は**いま出力したこの内容**についての内部状態（「この部分は読み切れていない」）を運べる。

### 1.3 統合方針

> **自己申告はUXチャネルとして守り、その信頼性を実測で担保する。**

- 制御（ゲート・介入・ループ予算）= 実測テレメトリのみ
- 表示（ユーザーの判断材料）= 自己申告 ＋ 実測の**二重表示**
- 較正されていない表示はユーザーの過信を招き、表示しないより悪くなり得る（Zhang et al. 2020）。
  よって申告を出すなら、実測との並置（ミスマッチの可視化）か条件繋留（ルーブリック）で「本物の信号」に近づける義務がシステム側にある。

## 2. 設計

### 2.1 Vitalsの二系統化

| 系統 | 値 | 算出 | 用途 |
|---|---|---|---|
| **申告（subjective）** | confidence / risk_note | LLMが応答時に申告（§2.3 ルーブリック繋留） | **表示のみ**。ユーザーの判断材料 |
| **実測（measured）** | success_rate / error_rate / repair_load / progress | システムが計測 | **制御＋表示** |

実測値の定義（初期版。全て移動窓 N=10 アクション）:

- `success_rate`: 直近アクションの成功率（既存の Pacemaker.execution_history から算出可能）
- `error_rate`: 直近アクションのエラー率（同上）
- `repair_load`: 直近ターンの AutoRepair 介入回数（SymOpsProcessor の warnings を集計。**モデル能力のセンサー**として後続設計でも使用）
- `progress`: 停滞検知（同一エラーの反復、状態の無変化）。「ループ回数」ではなく「進捗のない反復」を危険信号とする
  （根拠: 成功するエージェントは平均11.8回の反復を要する — [Meta, arxiv 2507.18755](https://arxiv.org/pdf/2507.18755)。反復自体は悪ではない）

既存4次元の行き先: confidence → 申告に残す ／ safety → 申告は `risk_note`（自由記述1行）に置き換え、制御は実測 error_rate へ ／ memory → 実測（トークン使用率から計算、申告不要） ／ focus → 実測 progress に吸収。

### 2.2 二重表示（本設計の核）

```
🦆 自信: 0.9（申告） / 0.7（実績）   ⚠ このアヒルは自信過剰気味です
```

- 申告値と実測値を**並べて**表示する。ミスマッチ自体が情報であり、誤較正を「隠れた危険」から「観察可能な性格」に変換する。
- 申告（主観）と計測（客観）の並置は問診とバイタル計測の関係と同型で、Companionコンセプトをむしろ深める。

### 2.3 ルーブリック繋留（申告の較正改善）

自由な数値申告（「0〜1で自信を」）は雰囲気で出される。検証可能な条件に繋ぐ:

```
confidence の申告規則:
- 対象ファイルをこのセッションで read_file していない編集 → ≤ 0.6
- テスト・実行で動作未確認 → ≤ 0.7
- 上記を満たし、変更が読んだ範囲に閉じている → 0.8 以上を許可
risk_note: 不確実な点が1つでもあれば1行で具体的に（例: "utils.py の呼び出し元は未確認"）
```

条件繋留された自己評価は素の数値申告より較正が良い。弱いモデルほど効果が大きい。

### 2.4 申告頻度の削減（プロンプト効率の回復）

- 現行: 「**全アクションの前に**4次元」（SYMOPS_SYSTEM_PROMPT §2）
- 新設計: 申告は**ユーザーが出力を読む瞬間のみ** — `::response` / `::duck_call` / 破壊的編集（edit_file / write_file 上書き / delete_*）の提案時
- 内部アクション（read_file, grep等）には申告不要。実測系が常時カバーする
- 削減効果: トークン税と遵守負担の大部分が消え、価値のある接点（ユーザーの読解時）は全部残る

### 2.5 制御系の置き換え

| 現行 | 新設計 |
|---|---|
| Safety Score Interceptor（申告 safety < 0.5 → ユーザー確認） | 廃止。破壊的操作の承認は既存の承認機構が既にカバー。実測 error_rate の連続悪化 → 慎重モード（後述） |
| Pacemaker check_health の SAFETY_DEPLETED 等（申告由来の減衰値を監視） | 実測値ベースに置換: ERROR_CASCADE（error_rate）、STAGNATION（progress）、REPAIR_OVERLOAD（repair_load 高 → フォーマット簡素化の示唆） |
| calculate_max_loops の vitals 係数 | 実測 progress / success_rate 係数に置換。**停滞がなければループ上限を緩める**（反復は悪ではない原則） |
| Vitals.decay()（ループごとの自然減衰） | 廃止（人工的な疲労は実測と無関係） |

### 2.6 較正の自動学習（フェーズD・任意）

- 申告 confidence をバケット化（0.0–0.5 / 0.5–0.7 / 0.7–0.9 / 0.9–1.0）し、各バケットの「そのターンの実成功」を記録
- 保存先: モデル別 JSON（例: `sessions/calibration/<provider>_<model>.json`）
- 得られるもの: 「このモデルの申告0.9は実質0.6」という**モデル別自信過剰係数** → 二重表示の実績側に反映、将来的にはフォーマットルーティング（repair_load と併用）の入力にもなる

## 3. 実装計画（フェーズ分割）

### Phase A: 機能分離（制御から申告を外す）— 最小で出荷可能
| # | 変更箇所 | 内容 |
|---|---|---|
| A1 | `companion/core.py` | Safety Score Interceptor を削除（破壊的操作の承認は既存機構に一本化） |
| A2 | `companion/modules/pacemaker.py` | check_health / calculate_max_loops を execution_history 由来の実測値ベースへ。decay 呼び出し廃止 |
| A3 | `companion/utils/response_format.py` ほか | 「全アクション前の申告」要求を削除し、§2.4 の頻度ルールに差し替え |

### Phase B: 実測Vitals＋二重表示
| # | 変更箇所 | 内容 |
|---|---|---|
| B1 | `companion/state/agent_state.py` | `MeasuredVitals`（success_rate / error_rate / repair_load / progress）を追加。申告系は `ReportedVitals`（confidence / risk_note）に再編 |
| B2 | `companion/modules/pacemaker.py` | 実測値の算出ロジック（移動窓）。repair_load は SymOpsProcessor の warnings を core 経由で受け取る |
| B3 | `companion/ui/console.py` | print_vitals を二重表示形式に変更（申告/実績の並置、乖離時の注記） |
| B4 | `companion/core.py` | ParsedResult.warnings → repair_load への配線 |

### Phase C: ルーブリック繋留
| # | 変更箇所 | 内容 |
|---|---|---|
| C1 | `companion/utils/response_format.py` / `companion/prompts/templates.py` | §2.3 の申告規則をシステムプロンプトに追加（削減した申告頻度ルールとセットで） |
| C2 | `companion/prompts/few_shot.py` | 応答例に「低confidence＋risk_note付き」の例を必ず1つ含める（弱いモデルは例がないと低値を申告しない） |

### Phase D: 較正学習（任意・後回し可）
| # | 変更箇所 | 内容 |
|---|---|---|
| D1 | 新規 `companion/modules/calibration.py` | バケット記録・係数算出・永続化 |
| D2 | `companion/ui/console.py` | 実績側表示に較正係数を反映 |

### テスト（各フェーズに付随）
- Pacemaker 実測値算出（窓計算・停滞検知）の単体テスト
- 「申告が制御に影響しない」ことの回帰テスト（高/低 confidence で実行経路が変わらない）
- 二重表示のフォーマットテスト
- ルーブリック文言が dump_prompt に出ることの確認

### スコープ外
- フォーマットルーティング自体（repair_load を入力にする将来設計の布石のみ）
- アヒルの表示演出の拡張（mood 表現等は本設計の後で自由に）

## 4. 検証基準

1. **遵守率**: 申告頻度削減後、応答時の申告フォーマット遵守率が現行（全アクション時）より向上すること（AutoRepair の vitals 修復介入回数で計測）
2. **判別力**: ルーブリック繋留後、申告 confidence と実成功の相関が素の申告より改善すること（フェーズDの記録で確認）
3. **制御の健全性**: 実測ベース介入が「停滞時に発火し、順調な長い反復では発火しない」こと（シナリオテスト）
4. **UX**: 二重表示が1行に収まり、通常時はノイズにならないこと
