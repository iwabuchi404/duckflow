# CodeCrafter v0.3.0 設計レビュー

## 概要
codecrafter v0.3.0 は、Sym-Ops v3.2 プロトコルを中核とするオープンソースのAIコーディングエージェントです。このドキュメントでは、以下の4つの視点から設計を詳細にレビューします：

1. **ループの仕組み** - Think-Decide-Execute サイクル
2. **プロンプト設計** - 動的構築とキャッシュ戦略
3. **ツール実装呼び出し戦略** - 登録、モード別フィルタリング
4. **メモリー管理** - 会話履歴、長期記憶、ナレッジ管理

---

## 1. ループの仕組み

### 設計概要
**Think-Decide-Executeループ**をSym-Ops v3.2プロトコルで実装。`DuckAgent.run()`がメインループを管理し、以下の状態遷移：
- `AgentPhase.IDLE` → `AgentPhase.THINKING` → `AgentPhase.EXECUTING` → `AgentPhase.AWAITING_USER`

### 強み
1. **状態機械の明確さ**: `AgentState`がSingle Source of Truthとして全状態を管理。
2. **マルチモード対応**: planning/investigation/taskモードで状況に応じた思考プロセス。
3. **Pacemaker介入**: 無限ループ防止、安全度低下時の自動停止。
4. **セッション永続化**: AgentStateの完全保存/復元で長時間作業をサポート。

### 改善点
1. **ループ制御の分散**: `core.py`に集中すべきロジックが`DuckPacemaker`、`CommandHandler`に分散。
2. **エラーハンドリングの一貫性**: 例外処理がツールごとに異なる。
3. **並行実行制限**: 複数タスクの並列実行サポートが限定的。

### 推奨改善
1. **集中ループコントローラの導入**: `core.py` にループ制御ロジックを一元化し、PacemakerとCommandHandlerの責務を明確化。
2. **統一エラー処理フレームワーク**: すべてのツールが `ToolResult` 型を返すように標準化。
3. **並行実行エンジン**: 独立したタスクの並列実行をサポートする `TaskExecutor` の拡張。
4. **ステートマシンの視覚化**: デバッグ用に状態遷移グラフを生成する機能の追加。

---

## 2. プロンプト設計

### 設計概要
**動的プロンプト構築**を`PromptBuilder`クラスで実装。4層構造でキャッシュ効率を最大化：
1. **静的システム指示層**: Sym-Opsプロトコルと哲学（常にキャッシュ）
2. **モード固有指示層**: ツール説明とモード別掟（同一モード内ではキャッシュ）
3. **Few-shot例層**: モード固有の具体例（同一モード内ではキャッシュ）
4. **動的コンテキスト層**: 状態、履歴、エラー（ターンごとに変化）

### 強み
1. **キャッシュ戦略の先進性**: Anthropic/OpenRouterの`cache_control`を活用し、トークン使用量を削減。
2. **モード別最適化**: planning/investigation/taskで異なるFew-shot例を提供。
3. **エラー対応力**: 直前ターンの構文エラーを`Correction Guide`として注入。
4. **構造化された出力**: Sym-Ops v3.2フォーマットでLLM出力を強制。

### 改善点
1. **プロンプトバージョン管理の欠如**: プロンプトテンプレート変更時の後方互換性保証がない。
2. **Few-shot例の限定的なカバレッジ**: 複雑なシナリオでの例が不足。
3. **動的コンテキストの肥大化**: `to_prompt_context()`が長くなりがち。
4. **国際化対応の欠如**: 日本語/英語の切り替えがハードコード。

### 推奨改善
1. **プロンプトバージョン管理の導入**: テンプレートにバージョン番号を付与し、マイグレーション戦略を確立。
2. **Few-shot例の拡充**: 実運用で収集した成功/失敗例をデータベース化。
3. **コンテキスト圧縮アルゴリズム**: 長い会話履歴を要約するLLMベースの圧縮層を追加。
4. **多言語対応**: プロンプトテンプレートを外部化し、言語リソースを動的ロード。

## 3. ツール実装呼び出し戦略

### 設計概要
**ツール登録とモード別フィルタリング**を`DuckAgent.__init__()`で実装：
- `register_tool()`で手動登録
- `UNIVERSAL_TOOLS`と`MODE_TOOL_MAPPING`でアクセス制御
- `get_tool_descriptions()`で動的プロンプト生成

### 強み
1. **モード別アクセス制御**: planningモードではファイル編集ツールを非表示にすることで安全性向上。
2. **動的ツール説明生成**: 関数シグネチャからSym-Ops形式の説明を自動生成。
3. **統一インターフェース**: すべてのツールがSym-Opsプロトコルに従う。
4. **サブLLM統合**: `generate_code`、`analyze_structure`で複雑な処理を委譲。

### 改善点
1. **手動登録の煩雑さ**: 新しいツール追加時に`__init__()`を修正する必要あり。
2. **依存注入の不足**: ツール間の依存関係（例: `file_ops`が`MemoryManager`を必要とする）が明示的でない。
3. **ツールバージョン管理の欠如**: ツールの互換性やAPI変更の追跡が困難。
4. **非同期/同期の混在**: 一部ツールが非同期、他は同期で実装されている。

### 推奨改善
1. **デコレータベースのツール登録**: `@tool(...)` デコレータでツール登録を自動化。
2. **依存注入コンテナの導入**: ツール間の依存関係を宣言的に管理。
3. **ツールAPI標準化**: 実行ハンドラを統一し、同期/非同期の抽象化レイヤーを導入。

## 4. メモリー管理とナレッジ管理

### 設計概要
`MemoryManager`が会話履歴のコンテキストウィンドウを管理。重要度スコアリングに基づき、履歴の刈り込み（Pruning）とアーカイブ（`ArchiveStorage`）を実行。

### 強み
1. **トークン予算の動的調整**: LLMのコンテキスト長に応じて`max_tokens`を動的に再計算。
2. **重要度ベースの刈り込み**: Recency, Role, Content特徴に基づいたスコアリングにより、重要な情報を保持。
3. **ギャップ要約**: 削除されたメッセージ群を要約し、コンテキストの連続性を維持。
4. **長期記憶へのアーカイブ**: 削除されたメッセージは`ArchiveStorage`に保存され、`recall`ツールで検索可能。

### 改善点
1. **スコアリングのブラックボックス化**: スコアリングロジック（`_calculate_importance`）が複雑で、調整が難しい。
2. **アーカイブの検索効率**: `ArchiveStorage`の実装詳細（`read_file @companion/modules/archive.py`を確認する必要がある）に依存。検索速度と精度が鍵。
3. **ナレッジベースの統合**: 現在は会話履歴アーカイブがメイン。外部ドキュメント（`docs/`）をLLMが参照する仕組みは、`search_archives`に統合されているか不明瞭（`MemoryTool`の実装依存）。

### 推奨改善
1. **スコアリングの透明化**: 各重み付けの決定根拠をドキュメント化し、設定可能にする。
2. **長期記憶の強化**: 外部ドキュメントや過去の成功事例をRAGでインデックス化し、`recall`ツールの精度を向上させる。
3. **ナレッジ抽出サブLLM**: 重要な決定事項（アーキテクチャ変更など）を自動抽出し、構造化ナレッジとして専用DBに格納する仕組みの導入。

## 結論と次のステップ

codecrafter v0.3.0 は、AIエージェントの制御構造として非常に洗練された基盤（Sym-Ops v3.2とマルチモード）を持っています。実用性を高めるためには、**ユーザー体験の向上**と**安定性の確保**に注力すべきです。

**次のアクションプラン**:

1. **安定性向上**: 統一エラーハンドリングフレームワークの整備（`ToolResult`の徹底適用）。
2. **保守性向上**: ツール登録のデコレータ化。
3. **プロンプトの洗練**: Few-shotの拡充とバージョン管理の検討。
