## 0. なぜこの文書があるか

従来のロードマップ（`docs/ROADMAP.md` Sprint 1〜4）では、協業系機能（Duck Debate / Molt Report / learnings.md）を「Sprint 4 の機能群の1つ」として扱っていた。しかし議論の結果、**協業ループは機能の1つではなく、Duckflow の中核コンセプト（存在意義そのもの）** という合意に達した。

## 1. 北極星

> **弱いLLMでも、ユーザーとの協業を通じて実用的な成果をコスト良く出しつつ、ユーザー自身も成長させる、継続的に賢くなる相棒**

構成要素:
- **弱いLLM前提** — 最強モデルを仮定しない（Duckflow 全設計の公理）
- **協業** — ユーザーの知恵をループに取り込む能動的補正
- **実用成果のコスト効率** — 安い・速いモデルで実用水準を担保
- **ユーザーの成長** — 判断に関与させ、理由を理解させる（依存によるスキル低下のアンチテーゼ）
- **継続的向上** — 学習が蓄積し、回を追って賢くなる（エージェントもユーザーも）

「相棒」は、代行する最強の道具ではなく、**共に進めることで双方が良くなる相手**。

---

## 2. 価値軸（品質競争ではない）

Duckflow は**強いLLMとの品質競争を正面からは戦わない**。別の価値軸で独自のニッチを確立する（ブルーオーシャン）。

| 軸 | 内容 | 強いLLM単体との差 |
|---|---|---|
| **V1 コストパフォーマンス** | 弱いLLMの安さ・速さ × 協業での質担保 = 実用水準を低コスト・低レイテンシで | 強いLLMは高コスト |
| **V2 ユーザー学習効果** | 判断関与・理由理解により**ユーザー自身が育つ** | 強いLLM単体は答えを出すだけで依存を生み、スキル低下を招きうる |
| **V3 継続的協業向上** | learnings 蓄積で回を追って良くなる | 単体LLMはセッション間で賢くならない |

> **合意事項:** 「強いLLMに勝つ」ことが目的ではない。V1/V2/V3 の複合価値で目的達成とする。とりわけ V2（ユーザー学習効果）は、強いLLMが構造的に到達できない領域であり、**「AI依存で頭が悪くなる」という現代の懸念に対するアンチテーゼ**になる。

## 3. 「筋の良い協業」の原則（設計基準・兼 検証基準）

協業ループの各機能は、以下4原則を満たす必要がある。**満たさない機能は「筋の悪い提案」であり採用しない。**

1. **認知負荷を上げすぎない** — 必要な時だけ立ち止まる。誤発動＝ノイズ＝信頼低下
2. **代行しすぎて思考を奪わない** — ユーザーの判断関与を残す。全部代行すると学習効果（V2）が死ぬ
3. **提案の質をシステム側で底上げする** — 弱いLLMの質の低さが協業ループに伝播しない工夫（プロンプト・Sub-LLM・検証）
4. **学習が蓄積され、次回に活きる閉ループ** — 一方通行（エージェント→ユーザー）で終わらない。recall で戻る

> これらは「協業機能を作ったか」ではなく「**協業が本当に機能しているか**」を測る基準でもある。

## 4. 協業ループの構造

3機能は独立機能ではなく、**1つのループの部品**。孤立させると全部中途半端になる。

```
  ┌──────────────────────────────────────────────────────┐
  │                                                        │
  ▼                                                        │
判断点 ──→ Duck Debate（立ち止まり・構造化選択・原則3で質底上げ）
              │
              ▼ 実行
         Molt Report（振り返り・学習の言語化・客観テレメトリで発動）
              │
              ▼
         learnings.md（蓄積: インデックス常時注入 + 詳細オンデマンド）
              │
              ▼
         recall（次回の関連場面で想起・判断精度向上）
              │
              └──────────────────────────────────────────┘
```

- **Duck Debate 単独** → 学習しない。毎回ゼロから同じ議論
- **Molt Report 単独** → 活用先がない。感想文で読み飛ばされる
- **learnings.md 単独** → 出力元も想起元もない。死蔵する

**最小ループ = Molt Report（出力）＋ learnings.md（蓄積）＋ recall（想起）**。これが回って初めて「相棒が賢くなる」が実証される。Duck Debate はその上に乗る「判断時の立ち止まり」オプション。

| 土台 | 従来の位置付け | 協業ループ中心での再解釈 |

## 6. 最大仮説・検証・効果測定

### 6.1 仮説
> **弱いLLM × 協業** が、**強いLLM単体**と同等の実用成果を、より低コストで（V1）、かつユーザー学習効果付きで（V2）、継続的に（V3）達成できるか。

品質で勝つ必要はない（合意済み）。ただし**逆リスク**も正直に扱う:
- 弱いLLMは協業の**提案自体の質も低い**。Duck Debate の提示質・Molt Report のレポート質が浅くなり、弱点がループに伝播しうる
- → 原則3（提案質のシステム底上げ）が、この伝播を防ぐ要。ここが技術的に一番むずかしい

### 6.2 効果測定の前提：計測困難性をどう扱うか

協業ループの価値の多く（特に「思考を奪わない」「ユーザー学習効果」）は**直接は測れない**。これを放置せず、以下の方針で扱う。

#### 指標の3層化
| 層 | 何を測るか | 例 | 限界 |
|---|---|---|---|
| **L1 直接（客観）** | システムが計測できるもの | コスト・発動 precision/recall・recall ヒット率・エラー率 | 本質（学習等）は映らない |
| **L2 proxy（行動推定）** | ユーザー行動から推定 | 提案流され率（ノイズproxy）・再質問率（理解proxy）・承認/却下比 | 代替指標に過ぎない |
| **L3 定性（人間観察）** | 人間が観察するもの | dogfooding 日誌・協業の手触り・学習の兆候 | 定量化困難・主観 |

#### 「証明」ではなく「早期検出」
L1/L2 は効果の**証明**ではなく**赤信号検出**に使う。「学習効果が上がった」は測れなくても、「思考を奪っている（原則2違反）」兆候は L2 で拾える可能性がある。定量指標は**安全網**として徹する。

#### 価値軸ごとの測定方針
| 軸 | 主な測定層 | 方針 |
|---|---|---|
| V1 コスト効率 | L1 | 客観的に十分測れる |
| **V2 ユーザー学習効果** | **L3中心・L2補助** | 最も測りにくい。特別扱い（後述） |
| V3 継続向上 | L1+L2 | recall ヒット率等のproxy |

#### V2（学習効果）の特別扱い — 「測る」のではなく「兆候を観察する」
「ユーザーが賢くなった」の直接測定は諦める。代わりに**行動シグナル**を dogfooding 日誌の観察項目にする（教育評価の「行動の変化」層）:
- 同じつまずきを繰り返さなくなったか
- ユーザーの指示が具体的になったか（「あれ直して」→「file_ops.py の _sanitize_content の挙動が〜」）
- エージェントに聞く前に自分で試みるようになったか

V2 の成否は、これらを定期的に振り返る程度の解像度で受け入れる。

#### Goodhart の法則を回避する
**「測りやすい指標（L1）に最適化しすぎると、測りにくい本質（V2）が犠牲になる」**。だから L1 は安全網に徹し、真の判断軸は L3（定性・dogfooding）に置く。発動精度を追い込むことが協業を良くするとは限らない、という警戒を持つ。

### 6.3 検証手段
- **dogfooding 最優先** — 第1の観察対象は「作者自身が Duckflow を使う自分」。L3 観察の主戦場
- **観測インフラの先行**（機能より先に入れる）— L1/L2 シグナルをログから取れる仕組みを先に立てる:
  - 発動精度（提案→承認/却下の precision/recall）
  - 提案流され率（L2・ノイズproxy）
  - recall ヒット率（L2・死蔵proxy）
  - 再質問率（L2・理解proxy）
- **成功判定の置き所** — Molt Report の「活用（行動変容）」は制御不能なので指標にしない。「学びが出力され、次回関連場面で recall された」までを成功とする（原則4の測定可能上限）
