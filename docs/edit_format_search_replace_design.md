## 1. 背景と動機

### 1.1 研究的根拠（検証済み）

| 知見 | 出典 |
|---|---|
| search/replace 形式は大型モデルで unified diff / line diff を23〜27pt 上回る（53% vs 30%/26%） | [Meta, arxiv 2507.18755](https://arxiv.org/pdf/2507.18755) |
| 理由: diff の `+`/`-` プレフィックスは学習データ（生コード）から乖離。プレフィックスなしの生コードが「LLMにとって自然」 | 同上 |
| Anthropic も複数方式を比較し「文字列置換が最も信頼できた」 | [Anthropic Engineering](https://www.anthropic.com/engineering/swe-bench-sonnet) |
| **確立された形式への軽微な構文変更ですら弱いモデルでは大幅に性能劣化する** | [JetBrains Diff-XYZ, arxiv 2510.12487](https://arxiv.org/html/2510.12487v1) |
| 寛容なパッチ適用（空白正規化等）を無効にすると編集エラーが9倍 | [aider](https://aider.chat/docs/unified-diffs.html) |
| LLM は行番号の扱いが極めて苦手 | 同上 |

結論: **「最も学習された形式」がプロンプト効率と遵守率の両方で最良**。aider 型 `<<<<<<< SEARCH / ======= / >>>>>>> REPLACE` は git コンフリクトマーカー＋aider の普及により、現存する編集形式の中で最も学習分布に乗っている。

### 1.2 現行 `find: |` 形式の構造的欠陥

現行形式は YAML ブロックスカラーで編集内容を運ぶ:

```
::edit_file @path
<<<
find: |
    （YAML分のインデントを足した対象コード）
replace: |
    （同上）
>>>
```

`companion/tools/file_ops.py` の `clean_block()` は**ブロックの最小インデントを剥がして**復元する。このため、**対象領域の全行が共通インデントを持つ場合**（クラスメソッド内部の編集＝最頻出ケース）、YAML分のインデントとファイル本来のインデントを区別できず、ファイル本来のインデントごと剥がれてバイト一致が壊れる。

これは「YAML インデント ⇄ ファイルインデント」の往復変換が**可逆である保証がない**というフォーマット自体の欠陥であり、モデルの遵守能力と無関係に失敗する。

## 2. 採用する設計

### 2.1 レイヤーの役割分担（重要）

- **アクション層（Sym-Ops）は変更しない。** `::action @target` ＋ `<<<`/`>>>` エンベロープは JSON 比較で弱いモデルへの優位が実証済みであり、研究知見（生テキスト > エスケープ付き構造化形式）とも一致する。
- 変更するのは **edit_file のコンテンツブロック内側の編集ペイロード構文のみ**。
- 設計哲学「厳守しなくても動く」は維持する。寛容性はフォーマットではなく**パーサー（AutoRepair）に宿る**ため、表面構文の変更と矛盾しない。

### 2.2 新形式（正規形）

```
::edit_file @path/to/file.py
<<<
<<<<<<< SEARCH
    def foo(self):
        return 1
=======
    def foo(self) -> int:
        return 2
>>>>>>> REPLACE
>>>
```

- SEARCH/REPLACE の内容は**ファイルに見えるままを column 0 から逐語で**書く。インデント変換は一切ない（read_file で見たものをそのまま書けば一致する）。
- 1ブロックに複数の SEARCH/REPLACE ペアを許可（現行の複数 edits 対応を踏襲）。
- 既存の Sym-Ops エンベロープ（厳密3文字 `<<<` / `>>>`）の**内側**に置く。エンベロープは7文字以上の git マーカーと厳密一致しないため干渉しない（§3.2 の既知バグ修正を除く）。

### 2.3 寛容文法（AutoRepair 拡張）

| 要素 | 厳密形 | 寛容パターン | 修復動作 |
|---|---|---|---|
| 開始 | `<<<<<<< SEARCH` | `^\s*<{4,}\s*(SEARCH)?\s*:?\s*$`（大文字小文字不問） | 正規形に正規化 |
| 区切り | `=======` | `^\s*={4,}\s*$` ※`={7}` 厳密一致を優先 | 正規形に正規化 |
| 終了 | `>>>>>>> REPLACE` | `^\s*>{4,}\s*(REPLACE)?\s*:?\s*$` | 正規形に正規化 |
| 終了忘れ | — | EOF まで終了マーカーなし | EOF で閉じる |
| ``` で包まれた | — | マーカーブロック全体が ``` フェンス内 | フェンスを除去 |

- 区切り `=======` の欠落は**修復不能**（SEARCH と REPLACE を分離できない）→ エラー＋ Correction Guide で正しい形式を例示（既存の `SyntaxErrorInfo` 機構を使用）。
- マーカー行は「同一文字の連続」なので `find:` のような単語キーより誤検出が少なく、修復しやすい。

### 2.4 後方互換

- 既存の `find: | / replace: |` 形式は**当面併存**させる（パーサーは両対応）。
- Few-shot・ツール説明・Correction Guide はマーカー形式に切り替える（モデルに見せるのは新形式のみ）。
- A/B ベンチマーク（§5）の結果を見て、旧形式の扱い（維持/廃止/コンフリクト時フォールバック専用）を決定する。

## 3. git コンフリクト衝突問題と防御（本設計の核心的リスク）

### 3.1 問題の定義

マーカーが「大量に学習されている」ことの裏返しとして、**実ファイルに同じマーカーが出現する**。典型はコンフリクト解消タスクで、SEARCH ブロックの内容自体が `<<<<<<< HEAD` / `=======` / `>>>>>>> main` を含む。

このときコンテンツとしての `=======`（git の区切りは正確に7文字でプロトコルと完全同一）を区切りと誤認する。**帯域内（in-band）でこの曖昧性を解決する方法は原理的に存在しない**。

さらに深刻なのは fail-open になる点: 誤認時の SEARCH 部（例: `<<<<<<< HEAD\nours のコード`）はコンフリクトブロックの**接頭辞として実ファイルにマッチしてしまう**ため、マッチ失敗で止まらず、ゴミを適用してファイルを破壊し得る。「search がファイルにマッチするか」によるバックトラック検証も接頭辞マッチに破られる。

### 3.2 防御（決定的ルーティング — モデルの判断に頼らない）

```
edit_file 実行時（パース前）:
  対象ファイルに git マーカー（^<{4,} で始まる行 等）が含まれるか検査
  ├─ 含まれる → マーカー形式のパースを拒否し、以下のいずれかへ誘導
  │     a) write_file による全体（または領域）書き換え
  │        ※コンフリクト解消は本質的に「壊れた領域の丸ごと書き直し」であり、
  │          search/replace 向きのタスクではない。性能上の損はない
  │     b) 衝突しない現行 find: | 形式へのフォールバック
  └─ 含まれない（通常ケース） → マーカー形式でパース
```

加えて二重の防壁:

- **健全性チェック（AutoRepair側）:** パース結果の REPLACE 部に git マーカー（`<<<<<<< ` / `>>>>>>> ` ＋ラベル）が残っている場合は誤パースの疑いとして**適用を拒否**し、Correction Guide で write_file への切り替えを促す。
- **既知バグの修正（形式に関係なく必要）:** `companion/utils/sym_ops.py` の `_fix_unclosed_blocks()` は `'<<<'` を部分文字列でカウントしているため、`<<<<<<< HEAD`（7文字）を2個と誤計上する。**行単位の判定（単独 `<<<` / `>>>` 行のみカウント）に修正**する。

### 3.3 一般化: 自己参照衝突の原則

これはマーカー形式固有ではなく、**帯域内フォーマット全てが持つ自己参照衝突**である（現行形式も `find: |` や単独 `>>>` を含むファイル——Duckflow 自身の few_shot.py やテスト——の編集で同型の問題を持つ。`::status` のダミーツール登録と同根）。

メタルール: **「編集対象がフォーマット自身のエコーを含むときは、戦略を切り替える」**。この検査はどの形式を採用しても実装する。

## 5. A/B ベンチマーク計画（2次元: 形式 × モデルtier）

**目的:** 移行の効果量を実測で決める。さらに §7 の tier→形式マッピングを当て推量でなく実証で確定する（研究知見は方向のみで、Duckflow のターゲットモデルでの閾値は未知）。

- **タスクセット（20〜30件）:**
  - 通常編集（単一行・複数行）
  - **共通インデント領域の編集（メソッド内部）** — 現行形式の欠陥が発火するケース。必須

  - **コンフリクト解消タスク＋gitマーカー入りファイルの編集** — ルーティングが正しく働くことの検証。必須
  - フォーマット・エコーを含むファイル（few_shot.py 等）の編集
- **比較軸（2次元）:**
  - 軸1 = 編集形式: 現行 `find: |` ／ SEARCH/REPLACE マーカー ／ `replace_function`・全体書き換え（階段の各段）

- **指標:** ①パース成功率（AutoRepair 介入回数含む） ②find/SEARCH マッチ成功率 ③エンドツーエンド編集成功率（意図した差分になったか） ④リトライ回数
- **判定:**
  - 各 tier で③が最良の形式を特定し、§7.2 の tier→形式マッピングの初期値を確定する
  - 「マーカーが壊れ始める tier 境界」（②③が現行・全体書き換えを下回る点）を特定し、フォールバック階段の降格閾値（§7.3）の根拠にする

## 6. 既知の限界・オープンな問題

1. **`=======` の帯域内曖昧性はゼロにならない**: RST 見出し下線（`====`）等、コンフリクト以外でも `={4,}` 単独行は実コードに存在し得る。`={7}` 厳密一致の優先と §3.2 の健全性チェックで緩和するが、原理的限界として認識する。
2. **複数 SEARCH/REPLACE ペアの区切り判定**: ペア間の境界（`>>>>>>> REPLACE` の次の `<<<<<<< SEARCH`）は明確だが、片方のマーカー欠落時の修復はペア数が増えるほど曖昧になる。寛容修復はペア数1のときに最も積極的に、複数ペア時は保守的に。
3. **旧形式の廃止時期**: ベンチ結果＋運用実感で判断。当面は両対応の保守コストを受け入れる。

## 7. マルチモデル対応（tier別フォーマット選択）

### 7.1 前提と最重要原則

編集形式の最適はモデル規模に依存する（検証済み）: 強モデルは search/replace が最良（Meta 53% vs 30%）、極小（0.5B）では search/replace が EM 0.00 で機能しない。aider も Gemini 用に diff-fenced を用意する等、モデル別形式切替を実践している。よってマルチモデル運用では形式選択を一級の設計要素とする。

> **最重要原則: 形式はシステムが決定してモデルに結びつける。LLM に形式を選ばせない。**

形式の選択肢を提示した時点で、低スペックモデルが扱う対象が増える。正しい設計は「どの形式を使うかをシステムが事前決定し、モデルのプロンプト（ツール説明＋Few-shot）には常に**1形式だけ**を見せる」。これにより形式が増えてもプロンプトの複雑度は1形式分に保たれ、「弱いモデルは少数の規則しか守れない」原則と両立する。

### 7.2 tier→形式マッピング（フォールバック階段への統合）

doc 1 の階段（マーカー → … → 全体書き換え）と `docs/code_navigation_context_design.md` の `replace_function` を、**形式スペクトラムの段**として一本化し、開始段をモデル tier で決める。

| tier | 開始形式 | 根拠 |
|---|---|---|
| 強（Claude / GPT-4o 級） | SEARCH/REPLACE マーカー | 簡潔・効率最良（Meta 検証済み） |
| 中（gpt-4o-mini, Llama-70B, GLM-4.5-air, Qwen-32B 級） | SEARCH/REPLACE マーカー＋ルーブリック強化 | Qwen-32B で EM 0.68、マーカーの主戦場 |
| 弱（小型無料モデル, 7B 級） | `replace_function` / 全体書き換え | マッチング自体が消滅。7B 級では関数単位 ≒ 全体書き換え（[arxiv 2604.27296](https://arxiv.org/html/2604.27296)、※未検証） |

※ 各 tier の最良形式は §5 の 2次元ベンチで実証的に確定する。Diff-XYZ は小モデルに udiff-l が最良という意外な結果を出しているため、マッピングは初期値とし、計測で上書きする。

### 7.3 tier 選択と実行時降格の統合

- **tier 選択（開始段）** と **実行時フォールバック（編集失敗で1段下げる）** は同じ階段上の操作として実装する。
- 例: 中モデルがマーカーで2回失敗 → tier に関わらず `replace_function` 段へ降格。
- これにより「モデル別選択」と「失敗時降格」が単一メカニズムに統合され、実装・思想ともに単純化される。

### 7.4 選択の入力源（段階導入）

1. **静的 config マッピング（まずこれ。aider 方式）**: `duckflow.yaml` の `available_models` 各エントリに `tier`（または `edit_format`）フィールドを追加。`/model` 切替時に該当形式向けへ Few-shot・ツール説明を再レンダリング。未知モデルのデフォルト = 中（マーカー）。決定的で予測可能。
2. **テレメトリ適応フック（後から）**: `docs/vitals_redesign_design.md` の `repair_load` と編集成功率を入力に、セッション中に実効 tier を自動降格（= 自己較正フォーマットルーティング）。本設計ではフックのみ用意し、本体実装は後続。

### 7.5 役割分割（「弱＋中の使い分け」の本命設計）

「弱と中を使い分ける」には2解釈がある:

- **解釈A: エージェント全体を切り替える** → §7.2〜7.4 の tier→形式マッピングで対応。
- **解釈B: 1セッション内で役割分担する** → こちらを本命とする。

既存の `SubLLMManager` と `generate_code` ツールを活かし:

> **ループ全体（探索・計画・進行管理）は弱い/安いモデルで回し、編集内容の生成だけ中モデルに委譲する。**

こうすると編集形式は簡潔なマーカーのまま据え置ける（マーカーを扱うのは中モデルだから）。失敗率の支配項（編集の中身の正確さ）だけ中モデルで潰し、残りを安く回す。研究的にも「特化 70B ≒ 素の 405B」（Meta 検証済み）が裏付ける、コスト効率の良い分割。
