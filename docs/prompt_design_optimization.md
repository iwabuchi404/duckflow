# プロンプト設計の最適化と動的注入ガイドライン

## 1. 現状の課題
現在の `companion/prompts/system.py` は静的な巨大文字列として構成されており、以下の問題があります。
- **トークン消費**: 全フェーズで全ツール定義を読み込むため、コンテキストを圧迫している。
- **フォーカス低下**: 実行フェーズに不要な調査ツールが提示されることで、モデルの注意力（Attention）が分散する。
- **保守性**: プロトコル定義とツール仕様が混在し、微調整が困難。

## 2. 推奨される動的設計（PromptBuilder）

### 2.1 構造的分離
ロジックとコンテンツを分離し、フェーズごとに必要なコンポーネントのみを結合します。

- **Core Protocol**: Sym-Ops v3.2の構文（`>>`, `::`, `<<< >>>`）。常に最優先。
- **Dynamic Tools**: フェーズ（Thinking / Investigation / Execution）に応じたツールセットの抽出。
- **Mode Instructions**: 現在のモード（Planning / Task / Investigation）に特化したガイドライン。

### 2.2 ツールカテゴリの定義
ツールを以下のカテゴリに分類し、動的に有効化します。
- `CORE`: `read_file`, `list_directory`, `note`, `response` (常時)
- `EDIT`: `edit_lines`, `write_file`, `generate_code` (Execution時)
- `SHELL`: `run_command` (Execution時)
- `INVESTIGATION`: `search_archives`, `analyze_structure`, `submit_hypothesis` (Investigation時)

## 3. プロトコル追従度向上のテクニック

### 3.1 肯定文による制約
「JSONを使わない」という禁止命令ではなく、「出力は常にSym-Ops v3.2形式に厳格に従う必要がある」という言語仕様としての定義に一本化します。

### 3.2 エラー・フィードバック・インジェクション
直前のターンで構文エラーが発生した場合のみ、プロンプトの末尾に「修正ガイド（例: `>>>` は行頭から開始すること）」を動的に挿入します。

### 3.3 Dynamic Few-Shot
成功した複雑な操作（例: 複数行の `edit_lines`）の履歴を1つだけ「ベストプラクティス」としてコンテキストに保持し、他は要約または削除することで、フォーマットの模倣精度を高めます。

## 4. 期待される効果
- **トークン削減**: ツール定義プロンプトの約30-50%削減。
- **精度向上**: 実行フェーズにおける「存在しないツールの呼び出し」の根絶。
- **開発効率**: プロンプトの断片化により、特定の指示（例: 調査の深さ）のみを独立して調整可能。
